# Lab1 Phase 1：SVG 编辑器（CLI）

## 架构方案

### 模块划分

本项目拟按职责划分为四个模块：命令行交互、编辑操作与历史管理、文档与图形模型、SVG 文件读写。各模块分别承担输入输出、操作组织、图形行为和文件处理工作，由统一的程序入口完成初始化和连接。

#### 1. 模块与职责

| 模块 | 目录 | 主要职责 |
|---|---|---|
| 命令行交互模块 | `src/cli/` | 提供命令行交互循环，显示提示符，读取用户输入；处理分词、双引号和注释；将解析后的输入交给应用模块，并向用户输出执行结果、警告或错误。 |
| 编辑操作与历史管理模块 | `src/application/` | 管理当前文档；根据命令名选择对应的命令实现，检查命令参数并组织执行；管理撤销和重做历史；协调图形模型与文件读写模块，完成编辑操作和文档操作。 |
| 文档与图形模型模块 | `src/model/` | 表示画布、普通图形和分组容器；维护图形 ID、父子关系和子节点顺序；封装图形的属性及移动、缩放、属性修改等行为；提供图形创建、查找及结构调整所需的能力。 |
| SVG 文件读写模块 | `src/io/` | 读取并解析 SVG 文件，将其转换为内部文档和图形对象；将内部文档转换为 SVG 并写入文件；处理文件访问和格式解析过程中产生的问题，将结果返回应用模块。 |

命令行交互模块负责通用的输入解析，命令名到具体操作的选择集中在编辑操作与历史管理模块中。图形的具体行为由图形模型中的类实现，例如矩形负责自身坐标与尺寸的变化，分组容器负责组织对子图形的操作。

#### 2. 程序入口

程序入口设置为 `src/Main.ts`，由 `Main` 类负责创建所需对象、连接各模块并启动命令行交互循环。

入口承担对象初始化和装配职责，具体的命令执行、图形编辑和文件处理分别交由对应模块完成。

#### 3. 模块协作示例

以用户输入 `move r1 10 20` 为例，计划采用以下执行流程：

1. **命令行交互模块处理输入。**  
   将输入拆分为命令名 `move` 和参数 `r1`、`10`、`20`，交给编辑操作与历史管理模块。

2. **编辑操作与历史管理模块组织执行。**  
   选择对应的移动命令对象，例如 `MoveCommand`，检查参数并通过当前文档定位 ID 为 `r1` 的图形，同时准备撤销所需的状态信息。

3. **图形模型执行移动。**  
   移动命令调用目标图形的移动方法。普通图形通过自身的实现更新几何属性；分组容器通过自身的实现组织子图形移动，从而实现整体平移。

4. **记录历史并显示结果。**  
   操作成功后，编辑操作与历史管理模块将该命令加入撤销历史，并返回执行结果；命令行交互模块向用户显示结果摘要。失败的操作应保持文档和历史状态不变。

文件读写操作通过另一条协作路径完成。例如执行 `save` 时，编辑操作与历史管理模块将当前文档交给 SVG 文件读写模块，后者完成序列化和文件写入，再由命令行交互模块显示保存结果。

该划分将图形自身的行为与操作历史管理分开，使普通图形和容器能够通过统一接口参与编辑，也使文件处理具有明确的职责边界。

### 设计模式的选择

本项目拟采用 Command 模式组织命令执行与撤销重做，采用 Composite 模式表示图形与容器的树形结构，并使用简单工厂机制集中创建图形对象。

Composite 已通过 Group extends Shape 落地；叶子和容器通过统一接口接受操作。

#### 1. Command 模式：组织操作与撤销重做

**选择理由**

编辑器需要支持多种编辑操作，并以一条编辑命令作为一个撤销单元。不同操作需要保存的恢复信息不同，因此将每次操作封装成命令对象，由命令自身负责执行和撤销，再由历史管理组件统一组织。

**计划落地方式**

在 `application` 模块中设置统一的命令抽象 `Command`，定义命令执行入口。可撤销的编辑命令进一步继承 `EditingCommand`，提供执行、撤销和重做行为。

具体编辑操作分别由对应的类实现，例如：

- `CreateCommand`：创建图形。
- `MoveCommand`：移动图形。
- `SetCommand`：修改属性。
- `DeleteCommand`：删除图形或子树。
- `GroupCommand`：组合已有图形。

每个命令保存完成撤销所需的信息。例如，移动命令保存恢复位置所需的状态；删除命令保存被删除的子树、原父容器和节点位置；分组命令保存各目标节点原来的父级和顺序。

设置 `HistoryManager` 管理撤销栈和重做栈，遵循以下规则：

1. 只有成功执行的编辑命令进入撤销栈。
2. 撤销或重做成功后，才调整两个历史栈。
3. 新的编辑命令成功执行后，清空重做栈。
4. 查询与显示操作不进入编辑历史。
5. 命令执行失败时，文档与历史状态保持不变。

对于成功执行的 `init`、`read`、`save` 和修改尺寸的 `canvas`，按作业要求禁止撤销和重做，直到下一条编辑命令成功执行后重新允许。

本项目拟将这些文档操作作为历史边界：操作成功后清空撤销栈和重做栈，后续编辑建立新的历史。这是本项目为明确历史边界而采用的实现约定。

#### 2. Composite 模式：统一普通图形与容器的操作

**选择理由**

SVG 文档具有树形结构：普通图形作为叶子节点，分组容器可以包含普通图形或其他容器。编辑器需要通过统一的操作方式处理两者，并支持容器嵌套。

**计划落地方式**

在 `model` 模块中设置图形抽象 `Shape`，封装图形的公共状态并定义移动、缩放、属性设置等操作。

普通图形分别由 `Rect`、`Circle`、`Ellipse`、`Line` 和 `Text` 等类表示，各类通过自己的实现处理对应的几何属性。

分组容器由 `Group` 类表示。`Group` 同样属于 `Shape`，并维护子图形集合。因此，容器可以包含普通图形，也可以包含其他 `Group`。

执行移动或缩放时，命令通过统一接口调用目标图形：

- 普通图形更新自身的几何状态。
- 分组容器组织子图形完成整体移动或缩放。

具体属性设置遵循各类型的属性白名单。删除、分组和移动归属等结构操作，由命令协调文档与容器提供的接口完成，以统一维护父子关系、节点顺序和 ID 管理。

通过这种结构，命令对象可以面向图形抽象组织编辑操作，具体行为由图形类通过多态完成。

#### 3. 简单工厂：集中创建图形对象

**选择理由**

CLI 的 `create` 命令和 SVG 文件读入都需要根据类型名创建具体图形。将这部分逻辑集中，可以使两种创建入口采用一致的类型支持范围和对象构造规则。

**计划落地方式**

在 `model` 模块中设置 `ShapeFactory`，集中处理类型名到具体图形类的映射，支持 `rect`、`circle`、`ellipse`、`line`、`text` 和 `g` 六种类型。

创建命令与 SVG 读取模块均调用同一个图形工厂。未知类型由工厂统一拒绝。

图形对象创建后，其移动、缩放和属性修改等行为通过多态执行。SVG 写出通过模型提供的统一描述或多态能力获取图形信息，由 `io` 模块负责 XML 编码和文件写入。

这里采用的是集中创建对象的简单工厂机制。

#### 4. 名称分派的集中管理与待重构项

按照作业要求，名称分派集中在以下两处：

| 分派位置 | 所在模块 | 当前职责 | 待重构方向 |
|---|---|---|---|
| 命令分发组件 | `application` | 将命令名映射到对应的命令实现 | 后续可改为命令注册机制，便于增加命令 |
| `ShapeFactory` | `model` | 将图形类型名映射到具体图形类 | 后续可改为图形提供者注册机制，支持类型扩展 |

上述两处在当前方案中明确标记为待重构项。本阶段先集中管理内置命令和六种图形类型，后续再根据扩展需求调整注册方式。

result1:Command 已通过 Command、EditingCommand、各具体命令和 HistoryManager 落地；简单工厂由 ShapeFactory 实现。Composite 目前只有统一的 Shape 抽象，Group 尚未实现。

### 依赖方向规则

本项目根据各模块的职责规定源代码依赖方向。箭头 `A → B` 表示模块 A 可以导入并使用模块 B 提供的类或接口，包括对其类型的引用。以下规则约束项目内部模块之间的依赖。

#### 1. 允许的依赖关系

| 模块或入口 | 允许依赖的模块 | 理由 |
|---|---|---|
| `cli` | `application` | 命令行交互模块将解析后的输入交给应用模块执行，并显示返回的结果。 |
| `application` | `model`、`io` | 应用模块需要通过图形模型完成编辑操作，通过文件读写模块完成文档读取和保存，并统一管理当前文档及操作历史。 |
| `io` | `model` | SVG 读取需要构建文档和图形对象，SVG 写出需要读取模型提供的结构与属性。 |
| `model` | 不依赖其他三个业务模块 | 图形模型负责文档结构、图形状态及图形行为，保持对命令行交互、操作历史和文件访问的独立性。 |
| `Main.ts` | `cli`、`application`、`model`、`io` | 程序入口负责创建对象、连接模块并启动程序，因此允许引用各模块完成装配。 |

除表中列出的关系外，其他跨模块依赖均视为需要检查和处理的依赖。模块内部的类可以根据职责相互协作。

#### 2. 具体边界约定

**命令行交互统一通过应用模块完成操作。**  
`cli` 将命令及参数交给 `application`，由应用模块组织执行。对于 `tree` 和 `show`，应用模块通过图形模型获取所需信息，整理为显示文本后返回，CLI 负责打印，因此 CLI 无须直接导入图形模型或递归遍历图形树。

**文件读写通过应用模块协调。**  
执行 `read`、`save` 时，由 `application` 调用 `io`。文件读写模块将处理结果、警告或错误信息返回给应用模块，再交给 CLI 显示，因此 `io` 无须引用 CLI。

**图形行为和操作历史分别管理。**  
`model` 中的图形类负责移动、缩放和属性修改等行为；`application` 中的命令对象及历史管理组件负责组织操作和撤销重做。图形模型无须了解命令行输入或撤销栈的管理方式。

**入口仅承担装配职责。**  
`Main.ts` 负责对象创建、依赖连接和程序启动。编辑操作、图形计算和文件处理分别由对应模块承担。

#### 3. 依赖检查方法

实现完成后，抽查各目录中源文件的 `import` 语句，对照上述表格检查跨模块引用。

重点检查：

- `cli` 是否直接引用了 `model` 或 `io`。
- `model` 是否反向引用了 `application`、`cli` 或 `io`。
- `io` 是否引用了 `application` 或 `cli`。
- `Main.ts` 是否承担了应由业务模块负责的处理逻辑。

发现不符合规则的引用时，应调整代码；如果确有必要修改依赖方案，则同步修订文档，并记录调整原因。

### 变化点假设

结合本阶段的功能要求和后续可能的扩展，预计变化主要集中在图形类型、编辑命令、交互入口和文件处理等方面。当前方案通过统一的图形抽象、命令抽象和明确的模块职责，为这些变化提供相对集中的修改位置。

考虑本阶段的目标和开发时间，扩展机制按实际需要逐步引入，具体取舍如下。

| 可能发生的变化 | 当前方案的准备 | 本阶段的选择与理由 |
|---|---|---|
| **增加图形类型或复合图形** | 普通图形和容器采用统一的 `Shape` 抽象，`Group` 表示组合结构；图形创建集中在 `ShapeFactory`。后续新增类型可以在这些位置扩展。 | 本阶段实现六种内置类型。新增类型时，仍可能需要增加图形类并修改工厂、参数处理和相关测试。后续引入 `box` 等复合图形及插件时，再增加类型注册、复合图形特有行为和读写还原机制。 |
| **增加编辑命令或调整命令语法** | 命令对象集中在 `application`，通过统一的命令抽象执行；可撤销操作由历史管理组件统一管理；CLI 负责通用的文本解析。 | 本阶段采用集中式命令分发。新增命令时，增加对应命令类，并同步调整分发、参数处理、帮助文本和测试。动态注册机制作为后续重构方向。 |
| **增加图形界面或其他操作入口** | 命令行输入输出与图形模型、编辑操作分开，新入口可以复用图形行为和部分应用逻辑。 | 本阶段围绕 CLI 实现交互。当前 `tree/show` 计划返回显示文本；未来增加图形界面时，可能需要在应用层增加结构化查询结果或其他交互接口，届时再根据具体需求调整。 |
| **扩大 SVG 文件的支持范围** | SVG 解析和写出集中在 `io`，图形状态和行为集中在 `model`，读入时复用统一的图形工厂。 | 本阶段优先满足作业规定的读写要求。新增标签、样式或变换语义时，根据其职责调整 `io` 和相应模型类，并增加保存与读回的一致性测试。具体支持范围和限制在实现后如实记录。 |
| **改变文档的存储途径** | 文件访问集中在 `io`，应用模块通过该模块协调读取和保存，文件处理具有明确的修改位置。 | 当前采用本地文件存储，并允许 `application` 直接依赖 `io`。如果未来需要支持其他存储途径，再考虑提取独立的存储接口；如果因此改变依赖关系，同步修订依赖规则和架构图。 |

其中，命令名称分派和图形类型名称分派对应前述两个待重构项。当前通过集中管理控制修改范围，后续再根据扩展需求决定如何引入注册机制。
